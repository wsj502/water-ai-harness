# 09 · 模型注册表与会话级切换：把「写死的模型」变成一等公民

> 阶段：M1（v0.2.0）｜ 代码：`packages/core/src/models.ts`、`packages/core/src/providers/index.ts`、`apps/server/src/index.ts`
> 本篇回答一个问题：**为什么 0.1.0 的「能接入但感觉写死」是真问题，以及模型选择权应该放在哪一层？**

## 问题复盘：四层写死

0.1.0 时代的模型链路（详见 issue #3）：

```
Web ──POST──► Server ──► agentLoop(provider, model=cfg.model)
                              ↑
              进程启动那一刻创建的唯一全局 provider
```

1. **Provider 是进程级单例**：server 启动时创建，运行时不可变
2. **模型是启动期配置**：flag > env > config.json，改一次要重启进程
3. **Web 零控制权**：设置页只读，没有 /api/models
4. **会话之间共享一切**：会话 A 和会话 B 无法用不同模型

对照 OpenCode：它的 `/models` 命令能在会话内即时切换，模型元数据来自 models.dev。
差距的本质是——**模型在 0.1.0 里只是一个字符串，不是注册表里的实体**。

## 设计：三层各管一段

```mermaid
flowchart LR
    subgraph 元数据["models.ts（纯数据）"]
        BI[内置表<br/>GLM/DeepSeek] --> MG[mergeModels<br/>id 冲突自定义优先]
        CF["~/.water/config.json<br/>models[] 自定义"] --> MG
    end
    subgraph 工厂["providers/index.ts"]
        RG[ProviderRegistry<br/>缓存 protocol|baseUrl|apiKeyEnv]
    end
    subgraph 会话["server"]
        SC["会话覆盖 s.protocol / s.model<br/>null = 跟随服务端默认"]
    end
    MG --> RG
    SC -->|"resolveSessionRuntime"| RG
    RG -->|acquire| P[Anthropic/OpenAI 适配器]
```

关键决策与理由：

| 决策 | 备选方案 | 为什么不选备选 |
|---|---|---|
| 元数据与工厂分离（models.ts / Registry） | 一个大 Registry 类 | 元数据要过 SSE 发给 Web（纯数据），工厂持有凭据不能序列化——职责天然分离 |
| 实例按 `protocol\|baseUrl\|apiKeyEnv` 缓存 | 每请求新建 | 适配器无状态，复用零成本；新建则浪费连接池与内存 |
| 协议随模型自动推断 | 允许独立指定协议+模型 | 「openai 协议配 glm 模型」是必然的 400 错，与其报错不如从根上杜绝 |
| 会话级覆盖可持久化（DB 两列） | 只存内存 | 重启丢配置 = 「切换是假的」，持久化后才是真功能 |
| 自定义模型 apiKeyEnv 只存名字 | 允许 config.json 存 key | 凭据红线；且值校验 `^[A-Z][A-Z0-9_]*$` 连「误贴 key」都能拦住 |

## 安全设计：为什么 Web 不能指定 baseUrl

这是本篇最重要的一个决策。读者第一反应可能是「让 Web 传 baseUrl 更灵活」，但：

```
Web ──"model=x, baseUrl=https://evil.com"──► Server ──apiKey──► https://evil.com
```

**凭据在服务端**，若前端能指定任意 baseUrl，等于把 key 转发给任意地址——这是一条
标准的 key 外泄通道（同源策略管不着服务端发起的请求）。所以 Water 的规则是：

- **baseUrl 只能来自服务端侧配置**（内置默认 / 环境变量 / config.json models[]）
- **Web 只能「选」**：协议 + model id，二者都在注册表白名单内
- `GET /api/models` 只返回元数据 + `hasKey` 布尔标记，永不返回 key

OpenCode 同样把 provider 配置留在本地文件、UI 只做选择——同一个安全模型。

## 协议层：SSE 里的模型标识

`turn_start` 事件新增 `model` 字段（向后兼容的可选字段）：

```
event: turn_start
data: {"type":"turn_start","turn":1,"model":"glm-4.6"}

event: text_delta
data: {"type":"text_delta","text":"pong"}
```

价值：事件流自带溯源——任务页回放、token 统计、多模型对比分析时，
不需要猜「这条回复是谁生成的」。这是「模型一等公民」在协议层的体现。

## 验证证据

### 离线 E2E（CI 常驻，16 项断言全绿）

`npm run test:e2e` 拉起构建产物、临时工作区隔离，覆盖：

- 注册表内容（双协议内置模型、mock 标记、凭据标记）
- 建会话带初始模型 → 协议自动推断
- SSE `turn_start.model` 与会话配置一致
- **运行时 PATCH 切换 → 下一条消息即用新模型（进程未重启）**
- reset / 双会话隔离 / 非法模型 400

### 真实 GLM 联调（2026-10-30）

`start-secure`（DPAPI 注入）启动 → `/api/models` 显示 glm-4.6 `hasKey:true`、
deepseek 系 `hasKey:false`（凭据矩阵真实反映）→ 会话选 glm-4.6 → 真实 SSE
流回包，`turn_start.model="glm-4.6"`。（DeepSeek 侧待 key，见备忘 issue #5）
